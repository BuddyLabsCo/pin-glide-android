# Pin Glide Service Contract Conflicts

Date: 2026-10-21

## Resolution update

Service release `v0.1.6` contains contract version `1.0.0`. It resolves
findings 2, 3, and 5: both YAML assets declare the independent contract
version, the four required arrays are non-nullable, and the credential token
descriptions distinguish Authorization-header credentials from F in the
refresh/logout body.

Finding 1 is handled in the Android generation design: parse the pinned
AsyncAPI 3.1 document with a pinned AsyncAPI parser, then pass the parsed
document to Modelina Kotlin. The direct Modelina invocation remains
unsupported and must not be used as the generation path.

The Android parent, functional, and architecture tickets have been updated
accordingly.

## Context

This note records conflicts between the current `pin-glide-service` release
contract and the Android Wayfinder requirements. It covers findings 1, 2, 3,
and 5 from the Android review. Finding 4 is intentionally excluded because it
is an Android ticket wording problem, not a service runtime defect; the
functional ticket has been updated separately.

Reviewed inputs:

- Service source: `BuddyLabsCo/pin-glide-service`, commit `08e76c8`.
- Published release: `v0.1.5`.
- Release assets: `openapi.yaml` and `asyncapi.yaml`.
- Android requirements: `BuddyLabsCo/pin-glide-android` issues 1, 2, and 4.

The findings below are not all runtime bugs. They are grouped by the contract
surface that fails when Android consumes the published release.

## Severity summary

| ID | Classification | Impact |
| --- | --- | --- |
| 1 | Blocking generated-code compatibility issue | The mandated Modelina Kotlin generation produces no models. |
| 2 | Release metadata and publication issue | Release tag, `version.json`, and both YAML versions disagree. |
| 3 | OpenAPI/runtime contract mismatch | Generated Android models allow `null` for arrays the service rejects or never returns as `null`. |
| 5 | Documentation contract defect | The shared token description says F belongs only in `Authorization`, while refresh and logout require F in the body. |

## Finding 1: Modelina Kotlin generates no models

### Requirement

Android issue 1, items A15, A16, A18, and A19 require WSS models generated by
Modelina Kotlin from the service's published `asyncapi.yaml`.

### Observed artifact

The published asset declares AsyncAPI 3.1.0:

```yaml
asyncapi: 3.1.0
```

See:

- `pin-glide-service/generated/protocol/asyncapi.yaml:2`
- `pin-glide-service/protocol/asyncapi.yaml:4`

### Reproduction

The following command was run against the `v0.1.5` release asset:

```powershell
npx --yes @asyncapi/cli@6.2.0 generate models kotlin `
  "$env:TEMP\pin-glide-v0.1.5\asyncapi.yaml" `
  --packageName com.buddylabs.pinglide.serviceevents `
  -o "$env:TEMP\pin-glide-kotlin-events" `
  --no-interactive
```

Output:

```text
Failed to convert root to MetaModel, defaulting to AnyModel
Kotlin generator, cannot generate this type of model, Root
Successfully generated the following models:
```

The process exits with status `0`, but the output directory is not created
and no Kotlin files are produced. Repeating the command against the local
generated description produced the same result.

### Impact

The Android architecture cannot use the mandated Modelina Kotlin path to
produce WSS models from the published release. A CI check that only checks
the process exit code reports a false success. The absence of generated
models blocks the WSS model placement and compatibility checks in Android
issue 4.

### Investigation points

- Confirm whether AsyncAPI 3.1 root documents are supported by the exact
  Modelina/Kotlin path used by Android.
- Check whether the release should publish a supported representation or
  whether the Android generation tool must change.
- Add an artifact check that fails when the generated model set is empty,
  in addition to checking the command exit code.

### Acceptance evidence

The chosen generation path must produce a non-empty set of Kotlin model files
from the exact pinned release asset, or the Android requirement must be
explicitly changed to a different generator or representation.

## Finding 2: Release tag and YAML versions disagree

### Requirement

Android issue 1 requires both release assets to be pinned from one explicit
release tag and to have their matching release/version and resolved
references verified. Android issue 4 requires the same provenance to be
recorded in the architecture and quality-gate design.

### Observed state

Release `v0.1.5` contains both assets, but both declare:

```yaml
info:
  version: 0.1.0
```

The repository release version is `0.1.5`:

```json
{
  "version": "0.1.5"
}
```

Relevant sources:

- `pin-glide-service/version.json`
- `pin-glide-service/generated/protocol/openapi.yaml:785`
- `pin-glide-service/generated/protocol/asyncapi.yaml:496`
- `pin-glide-service/internal/api/httpapi/router.go:27`
- `pin-glide-service/protocol/asyncapi.yaml:8`

The HTTP API version is currently hard-coded as `0.1.0`. The AsyncAPI
definition also hard-codes its own version. The release workflow exports,
lints, validates, and compares the assets for generated drift, but it does
not compare either `info.version` with `version.json` or the Git tag.

### Interpretation

There are two possible intended meanings:

1. `info.version` is the contract/API version, independent of the release
   tag. Both YAML files currently agree with each other at `0.1.0`, but the
   Android ticket must not call this a matching release version.
2. `info.version` is expected to match the published release. In that case
   the current `v0.1.5` assets are wrong, and the publication workflow is
   missing a required check.

The current ticket wording does not distinguish these cases, so a release
consumer cannot apply one unambiguous validation rule.

### Impact

An Android build cannot verify `release tag == YAML version` against the
current release. If the assets are later changed without a version change,
different releases can expose the same declared contract version, which
weakens provenance and change detection.

### Acceptance evidence

Choose one explicit versioning rule and make it verifiable:

- Contract version equals the release version and publication fails on a
  mismatch; or
- Contract/API version is separate from the release version, both YAML
  assets expose the same contract version, and the Android ticket describes
  the release-tag check separately.

## Finding 3: Required arrays are declared nullable

### Requirement

Android issue 1 item A08 defines `items` as the required array in a Message
upload. Item A09 and the functional ticket define a 207 response with one
result per input entry and a metadata response containing admitted
Deliveries.

### Observed OpenAPI

The following fields are declared as `type: [array, "null"]` in the
published OpenAPI:

| Schema | Field | Source |
| --- | --- | --- |
| `UploadRequest` | `items` | `pin-glide-service/generated/protocol/openapi.yaml:676` |
| `UploadResponse` | `results` | `pin-glide-service/generated/protocol/openapi.yaml:707` |
| `MessageDeliveries` | `deliveries` | `pin-glide-service/generated/protocol/openapi.yaml:224` |
| `ReceiverList` | `items` | `pin-glide-service/generated/protocol/openapi.yaml:547` |

The generated Kotlin client from OpenAPI Generator 7.26.0 consequently
contains nullable list types such as:

```kotlin
val items: kotlin.collections.List<UploadItem>?
val results: kotlin.collections.List<UploadResult>?
val deliveries: kotlin.collections.List<DeliveryView>?
```

### Runtime behavior

The upload reader rejects a JSON `items: null` value as an invalid envelope:

- `pin-glide-service/internal/api/httpapi/delivery/dto.go:87`

The 207 response always constructs a result slice, and the metadata response
always constructs a Delivery slice. A Message with no admitted Deliveries is
reported as `404 resource_not_found`, not as `deliveries: null`.

### Impact

The published schema permits an upload shape that the service rejects. It
also forces Android to handle `null` for successful response arrays even
though the runtime contract says those arrays are always present. This
weakens generated-model type safety and makes schema-first client tests
disagree with the server.

### Investigation points

- Determine whether the slice nullability comes from Huma's generated
  schema, the Go field types, or the shared schema projection.
- Confirm the intended schema for an empty 207 result and an empty Receiver
  list.
- Check generated Kotlin types against runtime serialization and rejection
  tests.

### Acceptance evidence

The published OpenAPI must make the required arrays non-nullable where the
runtime requires an array, and generated Kotlin models must reflect that
contract. Any nullable array that remains must have an explicit, tested
runtime meaning.

## Finding 5: F token is documented as Authorization-only

### Requirement

Android issue 1 item A02 requires M/U/F renewal using one operation ID and
attempt ordering. Android issue 2 specifies that F is supplied in the refresh
request body during renewal and can authorize logout when access has expired.

### Observed description

The shared `IssuedCredential.token` description says:

> Raw opaque credential; send it only in the Authorization header of an
> authenticated HTTPS or WSS request

Source:

- `pin-glide-service/internal/api/httpapi/identity/dto.go:14`

That description is reused for `CredentialBundle.userSession`,
`CredentialBundle.uploader`, and `CredentialBundle.refresh`.

### Actual transport

F is consumed from the JSON body for renewal:

```json
{
  "refreshToken": "F",
  "operationId": "...",
  "attempt": 0
}
```

Source:

- `pin-glide-service/internal/api/httpapi/identity/dto.go:43`

F can also be supplied in the logout body when no access credential is in
the Authorization header:

- `pin-glide-service/internal/api/httpapi/identity/dto.go:64`

The refresh and logout handlers read these body fields; the service runtime
behavior is correct.

### Impact

This is a documentation/contract defect, not a runtime authentication bug.
An Android implementation or generated SDK that follows the nested token
description may send F only as a Bearer credential and omit the required
body field, producing a validation failure. It can also cause misleading
client documentation and tests.

### Acceptance evidence

The OpenAPI description must distinguish:

- M/U credential transport and scope;
- F body transport for refresh and logout;
- which endpoints accept a body token versus an Authorization credential.

## Excluded finding

The earlier finding about failed 207 items requiring `error` is not included
here. The service runtime already emits a `BusinessError` for non-received
outcomes, but the stronger blanket requirement belongs in the Android
functional ticket wording. The intended Android rule is:

- `received` must omit `error`;
- `rejected` must carry an `error` code;
- `offline`, `send_failed`, `ack_timeout`, and `interrupted` use `status` as
  the primary outcome and may carry `error` as supplementary detail.
